# What Is & Specs 类 Type Module v1.0

## 1. 适用标准

适用于“什么是”“规格/参数”“定义、原理、类型、用途、差异”等事实解释型查询。目标是成为准确、可引用的答案来源，而不是把定义文伪装成教程或产品广告。

- 首屏必须给出简洁、可核验的直接定义；
- 数值、单位、协议、分辨率、兼容性和版本必须来自权威来源，并注明适用范围；
- 区分稳定知识、时间敏感规格、观点/推断和待确认事实；
- 产品最多作为 `implementation_tool` 或 `ultra_tip`，只能在读者理解概念和应用边界之后出现；
- 不能将未验证的“推荐工具”写成定义本身或唯一实现方式。

## 2. 类型流程

1. 建立 `Definition & Specification Model`：术语、同义词、上位/相关概念、权威定义、单位、版本、参数、来源和适用范围。
2. 判断读者需要的是纯定义、规格选型、机制解释还是应用理解，并据此决定模块比例。
3. 对所有动态参数做版本/日期核验；不确定值标注边界而非写成精确数。
4. 建立比较或类型表，只在其真的能辅助理解或选择时使用。
5. 完成清晰的实体图、规格表和误区/FAQ，再考虑可选工具。

## 3. 正文结构

1. Title / Meta / H1。
2. Direct Answer：首段直接定义，不以行业背景或产品广告开场。
3. Quick Specs / Key Facts：3–6 个最重要、可验证的参数或事实。
4. How It Works / Core Components：解释原理与各参数影响。
5. Types, Comparisons or Versions：说明差异与选择条件。
6. Uses, Limits and Common Misconceptions。
7. Optional Implementation Tool：仅说明把概念用于什么真实任务，以及能力边界。
8. FAQ 与结论。

## 4. 专属 Skill 与 QA

`Definition & Specification Modeler` 输出定义来源、术语关系、规格表、单位/版本、比较维度、常见误区、动态字段和产品适配结果。

失败条件：定义不在首屏、参数没有单位或来源、把版本限定结论泛化、把营销词当技术指标、用图片替代表格中的关键数值、用产品段替代核心解释。
