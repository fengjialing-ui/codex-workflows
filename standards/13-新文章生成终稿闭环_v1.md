# 新文章生成终稿闭环 v1.0

> **状态：现行强制标准。** 本文件解决新文章生成被错误降级为“初稿 + 回审交接包”的问题。它只适用于 `new_article`，不替代旧文优化/回审的 `12-旧文回审与终稿交付保障_v1.md`。

## 1. 先判定任务模式，不得由附件类型猜测

| 用户表达 | 正确模式 | 附件中的已有 Word 如何使用 |
| --- | --- | --- |
| “生成文章 / 写一篇 / 新内容 / how-to 文章” | `new_article` | 仅作选题、事实或表达参考；**不得**触发资产保留审计、优化或回审 |
| “优化 / 回审 / 提升现有文章 / 保留原文” | `optimization` | 执行 `12` 的资产审计和保留规则 |
| “重写现有文章”且明确批准 | `rewrite` | 执行 `12`，记录用户的重写批准 |

没有用户明确的“优化、回审、保留、修改现有文章”指令，任何 DOCX、URL 或旧内容都不能把新文章任务路由为回审。

## 2. 本项目的新文章默认交付

当用户在本工作流中请求“生成文章”而没有明确说“初稿、研究稿、仅 Markdown”时，默认 `delivery_level: publish_ready`，并在**文章生成流程内**完成最终内容包。只有用户明确要求初稿/研究稿时，才使用 `complete_draft`。

`publish_ready` 的含义是完整终稿内容包，不是“先交生成包，再要求用户另开回审任务”。独立 Article Review 仅在下列情况下触发：

1. 用户明确要求回审、优化、红线、旧文改稿或保留原有资产；
2. 用户明确要求额外的独立编辑复核；
3. 新文章已完成后，用户另行要求二次质量审计。

## 3. 新文章的固定终稿闭环

```text
任务模式 → 发布能力预检 → 关键词/SERP/事实 → Brief/方案池
→ 完整正文 → 实际视觉资产 → Markdown 与 Word 同步
→ Word 结构/Alt/链接检查 → 页面渲染与逐页检查
→ 发布检查器 PASS → ZIP / Final 声明
```

### 3.1 生成前的发布能力预检

在 SERP 前运行 `tools/Test-ArticleGenerationPreflight.ps1`，并将结果写入 `01_节点产出与状态总表.md`。检查以下能力：

- 可生成或取得所需真实视觉；
- 可创建 `06_完整文章.docx`；
- 可运行 DOCX 页面渲染器；
- 可运行 `tools/Test-ArticlePublishReady.ps1`。

渲染器不可用时，立即告知用户并记录 `Publish Ready` 将被阻断；可以继续完成“最终内容包”，但对外状态必须写为 `Content Complete — Render QA Blocked`，不得称 `Publish Ready`、`可直接发布` 或 `FINAL`。不得把这个问题拖到完成时才首次说明。

### 3.2 不可降级的终稿内容包

新文章的 `publish_ready` 必须直接生成下列内容，而不是只留视觉需求或回审交接：

- `06_完整文章.md`：完整可读文章，带实际图片路径、图注和来源；
- `assets/`：按文章类型、读者任务和已确认范围映射的真实场景视觉；
- `06_完整文章.docx`：嵌入实际图片、图注、可点击来源、真实 Word 表格、语义标题和有意义 Alt；必须恰有一个 `Heading 1`（与 Markdown H1 一致），并将每个 Markdown H2/H3 分别逐项映射为 Word `Heading 2`/`Heading 3`，不得把文章标题写成 Normal 段落或把模块标题误设为 H1；
- `07_视觉资产与映射表.md`：每张图的实际文件、插入位置、用途、Alt，以及 `Word embedded status: Pass`；
- `14_终稿交付清单.md`：明确写入唯一 Word 主交付、SEO、DOCX/Markdown 等价、关键词呈现和渲染状态；
- `qa-render.json`：最终同一 DOCX 的哈希、页面、渲染器与逐页结论。

文字图片规划、空的 `assets/`、单张通用示意图、未嵌图的 Word、仅 Markdown，均不构成终稿交付。

### 3.3 主关键词选择防呆

关键词表中搜索量最高的字符串不一定适合作为最终主关键词。研究后必须选择一个既代表核心意图、又能自然原样出现在 H1 与 Quick Answer 的主关键词，并在下列四处逐字一致：

1. `00_最终交付包索引.md` 的 `Primary keyword:`；
2. `05_文章结构与关键词映射.md` 的对应 `Covered` 行；
3. H1；
4. Quick Answer 正文。

未被选为主关键词的高量词保留为 P1/P2 变体，按意图自然覆盖；不得为了机械验收写出不自然 H1。

### 3.4 产品角色防呆

产品结论在写正文**之前**锁定。若推荐产品只能满足真实的次级对象或相邻意图，应标为 `ultra_tip`，并在该模块第一屏清楚写出不能解决的主任务边界；不得计入主 Methods，也不得包装成不支持的工具。若没有真实相邻需求，标为 `excluded` 并等待用户确认。

### 3.5 文件字段与检查器防呆

在正文前建立所有终稿包的正式文件名，禁止用“生成包索引”“生成质量报告”等自定义名称替代检查器所需文件。对 `new_article`，`13_内容资产保留审计.md` 必须只写：

```text
Review mode: new_article
```

`04_Content_Brief.md`、`05_文章结构与关键词映射.md`、`07_视觉资产与映射表.md`、`11_标准回审与质量报告.md` 与 `14_终稿交付清单.md` 必须逐字包含 `11` 的机器字段。正文/Word最后一次修改后，必须重新计算字数、重新生成 Word、重新做 Alt/链接/Markdown 残留检查、重新渲染，并运行统一检查器。

## 4. 明确禁止的失败模式

- 将“新文章生成”错误解释为“旧文回审”；
- 将仅含 Markdown、研究或视觉需求表的目录称为完整交付包；
- 为了流程边界，把最终 Word、真实图和 QA 留给“下一阶段”而不交付；
- 在最终 Word 生成后修改 Markdown 或 Word 却不重跑全量检查；
- 将实际渲染缺失隐藏在笼统的“已完成”里；
- 为通过关键词检查，把不自然的最高量词硬塞进 H1；
- 把图片工具写成视频工具，或在主方法结束后硬植产品；
- 使用与检查器不一致的文件名或缺失机器字段，最后才发现 P0 缺口。

## 5. 固定对外状态

| 条件 | 唯一允许表述 |
| --- | --- |
| 所有发布检查通过 | `Publish Ready` |
| 正文、Word、真实视觉和结构 QA 完成，但渲染器不可用 | `Content Complete — Render QA Blocked` |
| 研究、正文、视觉、Word或事实任一项未完成 | `In Progress` 或 `Complete Draft` |

不得把第二种状态称作“完整交付”“终稿”“Final”或“可直接发布”。
