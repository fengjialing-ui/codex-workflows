# 多类型文章调度与共享标准 v1.0

> **状态：现行标准。** 新建文章必须先读本文件，再读一个且仅一个 Type Module。当前支持：How-to、Top 评测、VS、泛主题、Alternatives、What Is & Specs。

## 1. 任务输入与路由

一个任务最少提供：文章类型、主题/主关键词、市场/语言与交付等级。关键词表、推荐产品和 Product Catalog 可选；目标用户、内容对象与搜索意图应在关键词和 SERP 研究后写入 Brief。系统不得根据产品名或旧文章猜测类型。

### 最小调用契约

日常调用只需提供以下核心字段：

```yaml
article_type: how_to | top_evaluation | vs | general_topic | alternatives | what_is_specs
topic: "..."
target_market: "..."
language: "..."
delivery_level: complete_draft | publish_ready
```

关键词表、推荐产品、站点、品牌语气和默认交付格式可以作为项目默认值保存在 `brief.md`；任务未覆盖时直接继承。若项目和任务都没有提供市场/语言，系统必须在 SERP 研究前要求补齐，不能擅自选择地区或语言。

| article_type | 何时使用 | 必读模块 |
| --- | --- | --- |
| `how_to` | 用户要完成一项操作或解决问题 | `07-How-to文章内容生成工作流_v5.md` |
| `top_evaluation` | Best / Top / Reviews / Buyer’s Guide / 推荐榜单 | `types/01-Top评测类_v1.md` |
| `vs` | 两个或多个明确实体的选择比较 | `types/02-VS类_v1.md` |
| `general_topic` | 泛知识、趋势、人物/作品、问题背景或混合信息需求 | `types/03-泛主题类_v1.md` |
| `alternatives` | 某产品、服务或方案的替代选择 | `types/04-Alternatives类_v1.md` |
| `what_is_specs` | 定义、原理、规格、参数、类型或用途 | `types/05-What-Is与Specs类_v1.md` |

类型不清晰时，先根据当前 SERP 与用户核心问题给出路由理由；不得同时套用两个正文模板。复合主题只选一个主类型，其他意图作为该类型内的模块处理。

## 2. 所有类型共用的核心流程

以下阶段对每个单主题任务都必须执行；Type Module 只定义其专属决策与正文结构。只有用户明确要求优化、回审、保留或修改已有文章时，才在第 1 阶段前转入 `12-旧文回审与终稿交付保障_v1.md`。附件中存在已有文章但用户请求“生成新文章”时，仍按本流程；旧文章仅是参考，不能自动改变路由。

1. **任务与范围闸门**：确认新建内容、类型、主题、市场/语言和用户已明确的限制；目标用户、主问题与内容对象可作为待验证假设，必须在研究后写入 Brief。
2. **关键词状态**：`formal_list`、`provisional` 或 `later_list`；默认 `intent-led coverage`，仅用户明确要求时使用 `strict_coverage`。
3. **独立研究护照**：记录检索词、市场、语言、设备、日期、SERP 前 10、3–5 个深度样本、PAA/论坛需求及来源。
4. **竞品机会矩阵**：输出 `Must Cover`、`Must Improve`、`Differentiate`、`Product Proof`、`Avoid`、`Verify`，并说明研究怎样确认或修正初步意图。
5. **事实与产品预校验**：读取本次 Product Catalog 与相应知识库；区分官方事实、已验证测试、案例、推断和待确认项。
6. **Type-specific Brief 与大纲**：只调用当前模块的结构、比较维度、证据门槛和产品位置规则。
7. **Evidence-first 完整初稿**：先完成用户核心答案，再写产品、CTA 和辅助内容；不交付大纲或说明报告代替正文。
8. **关键词、事实、结构和反模板化 QA**：问题回流到责任阶段，禁止用无依据的全文重写或统一评分掩盖缺陷。
9. **新文章终稿闭环**：当 `delivery_level: publish_ready`，按 `13-新文章生成终稿闭环_v1.md` 在本流程内完成真实图片、最终 Word、等价性、渲染和发布检查；独立 Article Review 仅在用户明确要求时追加。

## 3. 共享硬规则

- 批量任务只能共享字段、命名和检查器；不能共享 SERP、结论、结构、候选集、产品理由、正文或质量分。
- 所有事实性主张必须有来源或明确标为推断/待确认；不得伪造测试、用户评价、价格、速度、评分、排名或案例。
- 产品没有证据、与内容对象不匹配或不能解决真实相邻需求时，必须排除，不得为推广而制造场景。
- 标题层级连续且只有一个 H1；同级条目必须有一致语法与同等信息粒度。
- 关键词表是意图与覆盖依据，不是硬塞清单；无关、重复或语法不自然的词必须记录为 `Manual Review / Excluded`。
- 视觉需求必须描述真实用户场景、界面状态、素材对比或决策画面；不得把白底文字卡、抽象箭头图或占位符当作完成配图。
- 旧文回审默认保留有效内容与原图；新图用于补充场景、步骤和结果理解。最终 Word 必须是完整可发布文章，不能由审核说明、图表计划、关键词表或单张示意图替代。
- 不得把同一段落、同一方法顺序、同一产品结论或固定评分换词后用于不同主题。

## 4. 产品角色：共享输入、类型化输出

Product Catalog 的事实字段全类型共用，但文章角色由 Type Module 决定：

| 角色 | 可用于 | 含义 |
| --- | --- | --- |
| `formal_method` | How-to | 直接完成主任务的正式方法 |
| `ranked_candidate` | Top / Alternatives | 符合公开入选标准、可公平比较的候选项 |
| `comparison_subject` | VS | 明确被比较的对象；不预设胜者 |
| `implementation_tool` | What Is / 泛主题 | 用于把已解释的概念应用到真实任务的工具 |
| `ultra_tip` | How-to / 泛主题 / What Is | 主任务完成后的相邻需求补充 |
| `excluded` | 所有类型 | 不相关、无证据、不匹配或有误导风险 |

任何产品的角色、位置、证据和限制都必须写进 Brief。产品不是默认“第一名”“胜者”或“最佳平衡方案”。

## 5. 共用 Skills

所有类型调用以下 Skills；详细输入输出见 `09-多类型内容生成Skills_v1.md`：

1. `Task Router`：识别文章类型和边界；
2. `Keyword & Intent Planner`：建立正式或临时 Keyword Map；
3. `Research Passport & SERP Analyst`：完成独立 SERP 和竞品正文研究；
4. `Fact & Product Verifier`：核验产品、第三方、数据与来源；
5. `Content Opportunity Planner`：将机会矩阵变成 Brief；
6. `Visual Requirements Planner`：建立真实场景导向的视觉需求包；
7. `Cross-type QA & Handoff`：做结构、事实、关键词、反模板化和交接检查。

当前 Type Module 再额外调用专属 Skill；不得为了省事跳过共享核心。
