# 内容生成工作流与测试 v4.2

## 1. 完整工作流

### 阶段 1：任务进入

输入关键词、目标页面、产品、市场、语言、参考资料、目标 URL，以及新建或更新类型。

更新任务先锁定原文中的 Quick Answer、use case、正确步骤、专业案例、FAQ 和有效结论。

### 阶段 2：SEO 关键词分析

输出主关键词、次关键词、长尾词、语义词、场景词、PAA/FAQ 词，以及关键词到 Title、H 标签、正文和 FAQ 的映射。

### 阶段 3：初步搜索意图假设

根据关键词、页面类型和已有数据，初步判断用户要完成的任务、主要场景、预算、设备、能力、结果预期和希望比较的方案类型。

该结果用于筛选竞品，不是最终搜索意图结论。

### 阶段 4：SERP 样本选择与竞品内容分析

记录目标市场、语言、设备和日期，获取自然搜索结果前 10 名，深度分析 3 至 5 个与目标意图和页面类型一致的核心竞品。

分析：

- 用户需要什么内容和决策帮助
- 竞品覆盖的结构、Methods、关键词、场景、步骤、案例、FAQ 和 Verdict
- 排名页面在内容层面可能做对了什么
- 竞品的内容深度、可执行性、E-E-A-T、UX 和转化逻辑
- 竞品共性、遗漏、错误和可超越机会

输出内容机会矩阵：

- Must Cover
- Must Improve
- Differentiate
- Product Proof
- Avoid
- Verify

### 阶段 4A：搜索意图综合判定

结合初步假设、SERP、竞品内容、PAA、相关搜索和论坛需求，确定最终主意图、次意图、场景、决策问题和内容边界。

必须说明竞品分析确认、修正或否定了哪些初步判断。

### 阶段 4B：解决方案研究

根据最终意图和竞品分析，收集并去重官方、免费、手动、在线、桌面、专业、论坛验证和自有产品方案。

竞品已有方案只是候选来源，必须验证有效性，不能直接照搬。

### 阶段 5：Methods 决策

先形成完整候选方案池，再按有效性、场景差异、用户门槛、风险和决策价值去重、合并、保留与排序。常见成稿为 2 至 4 个方法，但不是硬性生成数量；最终方法矩阵逐项写明场景、用户、步骤摘要、预期结果、成本、优点、限制、证据和保留/淘汰理由。

闸门：

- 自有产品必须进入候选池接受评估；仅在适配当前问题时进入最终矩阵
- 产品计入 Methods 总数
- 多方案意图不能只保留一个 Method
- 产品不能在矩阵完成后作为独立推荐追加
- “Best”定位必须有比较依据
- Methods 必须回应竞品分析发现的真实用户需求和内容差距
- 不得固定产品排在第一、第二、第三或最后；按比较证据安排最合适位置

### 阶段 5A：产品适配与 Ultra-Tips 决策

在正式 Methods 定稿前，为每个指定产品输出产品角色：`formal_method`、`ultra_tip` 或 `excluded`。

判断顺序：

1. 当前文章的核心内容对象是什么，例如图片、视频、GIF 或 PDF
2. 产品是否明确支持该内容对象
3. 产品是否能直接完成用户的核心任务
4. 如果不能直接完成，用户完成主任务后是否存在真实且相关的相邻需求
5. 相邻需求是否有明确产品事实、操作步骤和边界

决策规则：

- `formal_method`：进入正式 Methods 矩阵，计入 Methods 数量，并与其他方案并列比较
- `ultra_tip`：不进入正式 Methods 矩阵；在主要 Methods 完成后以 Ultra-Tips 补充推荐
- `excluded`：不进入文章，并记录排除理由

Ultra-Tips 的硬性闸门：

- 不得出现在 Quick Answer、正式 Methods 总览或主方法之前
- 必须明确说明产品不解决当前主任务的哪一部分
- 必须说明它解决的相邻需求、具体步骤和限制
- 不得用 Ultra-Tips 凑方法数量、替代正常方案或制造产品适配假象

### 阶段 6：产品事实预校验

在产品 Method 设计前，校验产品功能、模型、格式、平台、步骤、参数、限制、版本和可用案例。资料不足时标记待确认，禁止模型补猜。

### 阶段 7：场景化产品 Method 设计

输出：

- 场景诊断与用户痛点
- 普通方法不足
- 功能/模型与场景映射
- 完整操作步骤及场景化设置
- 预览、异常处理和导出建议
- 专业案例或明确标记的示例工作流
- 优点、限制和比较依据
- CTA 的合理位置

产品 Method 在此阶段设计完成，不在正文完成后“植入”。

如果阶段 5A 的产品角色为 `ultra_tip`，不执行正式产品 Method 设计，而是进入“Ultra-Tips 产品推荐设计”分支：

- 主任务完成后的相邻场景
- 产品为何适合该相邻场景
- 产品不适用当前主任务的明确说明
- 场景化操作步骤
- 格式、大小、登录、隐私、结果和版本限制
- 补充 CTA 与合理位置

### 阶段 8：Content Brief

Brief 必须固定：

- 搜索意图
- 方法矩阵与顺序
- 产品 Method 规格
- 关键词与章节映射
- Quick Answer、方法总览、比较、use case、案例、FAQ 和 Verdict
- 每个模块的验收条件
- 竞品共性、内容差距和排名内容的可能优势
- 我们必须写得更好的具体模块
- 产品角色及其理由；若为 Ultra-Tips，必须固定补充模块的位置、标签、场景、边界和 CTA
- 至少一个可验证的差异化价值

### 阶段 9：H 标签规划

先生成标题树：

- 一个 H1
- H2 主要模块和同级 Methods
- H3 子问题、步骤组、参数或案例
- 非标题模块清单

程序预检 H1 数量和标题跳级，未通过不得生成大纲。

### 阶段 10：人工确认 Brief 与方法矩阵

确认：

- 搜索意图是否正确
- Methods 是否覆盖主要用户场景
- 产品是否确实适合作为推荐 Method
- 产品事实和案例是否足够
- “Best”定位是否有依据
- 关键词和 H 标签规划是否合理

### 阶段 11：大纲生成与审核

审核闸门：

- 方法数量与矩阵一致
- 产品 Method 与其他 Method 同级
- 产品 Method 有场景、详细步骤和案例安排
- Quick Answer、比较、use case 和 Verdict 完整
- H1 唯一且 H2/H3 层级正确
- 大纲落实竞品内容机会，而不是复制竞品结构
- 若存在 Ultra-Tips，必须放在主要 Methods 之后，并与正式 Methods 使用不同的模块标识

任一项不通过，不进入正文。

### 阶段 12：分章节正文生成

按批准后的大纲生成。所有 Method 使用统一结构，产品章节读取已经确认的“产品 Method 规格”。

禁止正文阶段：

- 临时删除其他 Methods
- 把产品改成 Methods 后的独立广告章节
- 用通用卖点替换场景化内容
- 将详细步骤缩成 Download、Upload、Enhance、Export

若产品角色为 `ultra_tip`：

- 先完成所有正式 Methods，再生成 Ultra-Tips
- 使用明确标题，例如 `Ultra-Tip: Clean the Image Version` 
- 不把产品写成当前视频、GIF 或其他主对象的解决方案
- 不把 Ultra-Tips 的步骤写入正式 Methods 比较表

### 阶段 13：产品 Method 证据审核

检查场景、功能映射、步骤、参数、案例、结果、限制和比较证据。产品若被称为最佳方案，必须能从比较表和案例中找到依据。

### 阶段 14：事实校验

对产品、第三方方案、案例和结果表述逐项校验。无来源的测试结果、评价、参数和承诺不得保留。

### 阶段 15：SEO 优化

检查 Title、Meta、唯一 H1、H2/H3、关键词自然度、FAQ、内链和图片 alt。SEO 优化不得改变已批准的方法数量和场景逻辑。

### 阶段 16：标准回审

使用正式标准逐条回审并提供文章位置证据：

- 搜索意图是否完整满足
- Methods 是否足够且有场景差异
- 产品是否为正式 Method
- 产品步骤是否详细可执行
- 产品是否有专业案例和真实边界
- “Best”结论是否有证据
- H1 是否唯一、标题树是否合规
- Quick Answer、use case、FAQ 和 Verdict 是否完整
- 竞品 Must Cover 是否合理覆盖
- Must Improve 和 Differentiate 是否真正落实
- 是否解释了为什么本文比竞品更有帮助
- 若使用 Ultra-Tips，是否先完整解决主任务、位置是否合规、边界是否透明、步骤是否真实可执行

### 阶段 17：质量审核与回流

- 初步意图或竞品筛选问题 -> 初步搜索意图假设
- 竞品样本或分析问题 -> SERP 样本选择与竞品内容分析
- 最终意图问题 -> 搜索意图综合判定
- 方案遗漏 -> 解决方案研究
- Methods 数量或排序问题 -> Methods 决策
- 产品事实问题 -> 产品事实预校验
- 产品场景、步骤或案例问题 -> 场景化产品 Method 设计
- 产品对象不适配但存在相邻需求 -> 产品适配与 Ultra-Tips 决策
- Ultra-Tips 位置、边界或步骤问题 -> Ultra-Tips 产品推荐设计
- H 标签问题 -> H 标签规划
- 结构问题 -> Content Brief 或大纲
- 正文执行问题 -> 对应章节生成
- SEO 问题 -> SEO 优化

不得用全文重写替代有明确责任节点的局部回流。

### 阶段 18：导出

保存标准版本、Skill 版本、方法矩阵、产品事实来源、审核证据、修改记录和最终文章。

## 2. 测试建议

### 2.1 固定测试集

How-to 首轮至少使用：

- 2 篇多方法主题
- 2 篇产品明显适合但容易生硬推荐的主题
- 2 篇主内容对象与产品对象不一致、但存在合理相邻需求的主题，用于测试 Ultra-Tips
- 1 篇官方方案应优先的主题
- 1 篇只有有限可行方案的主题
- 2 篇已有高价值模块、只允许增量优化的旧文章

### 2.2 结构指标

- H1 唯一率：100%
- 标题层级合规率：100%
- 方法矩阵与正文一致率：100%
- 产品作为正式 Method 的命中率：100%
- 多方案主题只生成一个 Method 的错误率：0%

### 2.3 产品 Method 指标

- 场景诊断完整率
- 功能与场景映射准确率
- 步骤可执行率
- 专业案例完整率
- 产品事实错误率
- “Best”结论证据覆盖率
- 产品推荐自然度与说服力人工评分
- Ultra-Tips 适配判定准确率
- Ultra-Tips 边界透明率
- Ultra-Tips 相邻场景步骤可执行率
- Ultra-Tips 误导主任务概率：0

### 2.4 搜索意图指标

- 主要意图覆盖率
- 场景词覆盖率
- 用户方案选择问题覆盖率
- Quick Answer 与 Methods 一致率
- use case 分流有效率

### 2.5 竞品分析指标

- 核心竞品样本有效率
- 竞品结构与正文分析完整率
- 用户意图结论证据覆盖率
- Methods 去重完整率
- Must Cover 落实率
- Must Improve 落实率
- 差异化价值完成率
- 竞品营销表述误用率
- 竞品结构复制率

### 2.5 回归测试

每次修改标准或 Skill 后，使用同一测试集比较：

- 是否保留 Quick Answer、use case、正确步骤、案例和 FAQ
- 是否新增了有价值的 Method，而不是增加重复内容
- 产品章节是否更具体，但没有变得臃肿
- 不兼容产品是否被正确降级为 Ultra-Tips，而不是被误写成正式 Method
- Ultra-Tips 是否保留主任务解决方案之后的补充价值
- H 标签修正是否只改层级，没有删掉有效内容
- 人工修改时间和返工次数是否下降

## 3. 交付检查清单

- [ ] 只有一个 H1
- [ ] 搜索意图先于 Methods 决策
- [ ] Methods 覆盖不同用户场景
- [ ] 自有产品是其中一个正式 Method
- [ ] 产品角色已判定为 formal_method、ultra_tip 或 excluded
- [ ] 不兼容产品未被写成正式 Method
- [ ] Ultra-Tips 位于主 Methods 之后，且明确说明相邻需求和限制
- [ ] 产品 Method 与其他 Method 同级
- [ ] 产品 Method 有场景诊断和功能映射
- [ ] 产品步骤详细、可执行且事实正确
- [ ] 产品有专业案例或明确标记的示例工作流
- [ ] “Best”结论有比较和案例依据
- [ ] Quick Answer、比较、use case、FAQ 和 Verdict 完整
- [ ] 最终回审记录了每项标准的文章证据位置
- [ ] 已分析当前 SERP 和至少 3 个核心竞品
- [ ] 已说明用户需要什么、竞品写了什么
- [ ] 已分析排名内容在内容层面可能做对了什么
- [ ] 已形成 Must Cover、Must Improve、Differentiate、Product Proof、Avoid、Verify
- [ ] Brief 和大纲落实了具体超越策略
