# Top 评测类 Type Module v1.0

## 1. 适用标准

适用于 Best、Top、Reviews、Buyer’s Guide 和按“最适合谁”推荐多个产品/服务的文章。文章的任务是帮助读者做选择，不是把产品目录改写成排名表。

### 入选与证据规则

- 先定义候选池、入选门槛、比较维度和淘汰理由，再确定数量、顺序或第一名；
- 仅能比较可核验且同一任务下真正可替代的候选项；
- 价格、平台、功能、限制、评分和排名依据必须有当次来源与日期；
- 只有具备可复查的测试计划、素材、环境、结果和限制时，才能写 `tested`、测试评分或性能胜者；
- 没有实测时，使用“基于公开资料/已核验资料的编辑评估”，不得伪造第一人称体验、用户评论或对比数据；
- 自有产品必须满足同样入选标准，作为 `ranked_candidate` 而非预设 Best Overall。

## 2. 类型流程

1. 在共享研究后建立 `Evaluation Matrix`：候选、用户场景、价格模式、平台、能力、限制、证据等级与淘汰理由。
2. 确定读者的决策维度与权重；权重必须解释为何适合当前主题，不能套用固定评分。
3. 对每个入选项完成同等深度的事实核验；证据不足的项只能降级、标待确认或排除。
4. 建立排名与 Use-case Picks，并让首屏、比较表、单品评测与结论完全一致。
5. 生成完整初稿，执行专属 QA 后交接回审。

## 3. 正文结构

1. Title / Meta / 唯一 H1：年份与数量只能在有事实依据时使用。
2. Introduction：说明选择难点、文章覆盖范围和评估依据。
3. Quick Picks：用场景回答 Best Overall / Best Budget / Best for…；每个结论必须有简短理由。
4. At-a-glance Comparison Table：只比较真的可比字段。
5. How We Evaluated：明确资料来源、测试状态或编辑评估边界。
6. Ranked Reviews：每个候选项使用相同卡片——定位、Best for、关键能力、限制、价格/兼容性、证据说明。
7. Buying Guide / Recommendation by Use Case。
8. FAQ 与 Final Recommendations：按读者场景给出明确选择，不重新制造无证据的总冠军。

## 4. 专属 Skill 与 QA

`Evaluation & Ranking Designer` 必须输出候选池、入选规则、比较维度、证据等级、排名理由、未知项和排除理由。

以下任一情况失败：固定数量凑榜、第一名预设为自有产品、比较字段不一致、把官网文案写成实测、虚构评分/价格/用户评价、单品篇幅与证据标准明显不公平。
