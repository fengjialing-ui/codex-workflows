# 高转化 How-to 文章内容结构标准 v3.2

## 1. 文章目标

How-to 文章首先满足用户寻找解决方案的意图，再通过客观比较让产品方案成为最有说服力的选择。

- 提供完整、可执行的解决方案，而不是只介绍一种做法
- 当自有产品能够直接处理当前内容对象和核心任务时，将其作为 Methods 中的一个正式方法，与其他方法并列
- 当自有产品不能直接处理当前内容对象，但能解决相邻且真实的补充需求时，只能作为明确标注的 Ultra-Tips 补充推荐
- 通过场景匹配、详细步骤、结果证据和专业案例体现产品优势
- 帮助用户判断不同方法分别适合谁、能解决什么、有什么限制
- 同时满足 SEO、AIO、GEO 和转化要求

产品不是 Methods 之后的广告模块，也不是脱离用户问题的“最佳工具推荐”。如果产品能够直接解决该问题，它必须从 Methods 研究阶段进入方案矩阵，并在大纲中占据一个完整 Method；如果产品不能直接解决当前主任务，只能在完成主要解决方案后，以 Ultra-Tips 形式补充，并明确说明它解决的是相邻需求而非当前主任务。

## 2. H 标签规则

### 2.1 Title 与 H1

- 每篇文章有且仅有一个 H1
- H1 表达整篇文章的唯一主主题，自然包含主关键词
- Title 与 H1 可以接近，但不能机械重复
- Method 名、Quick Answer、Introduction、Verdict、CTA、产品名和普通强调语不能设为 H1
- 不能为了视觉放大而使用 H1；视觉样式与语义层级必须分开

### 2.2 H2、H3 与步骤

- H2 用于同级主要模块，包括每个独立 Method、比较、案例、FAQ 和 Verdict
- 当多个 Method 是文章主体时，每个 Method 使用同一标题层级，通常为 H2
- H3 用于 Method 内的适用场景、操作步骤组、参数建议、专业案例、优缺点或子问题
- 单个操作步骤优先使用有序列表；只有步骤本身需要独立解释或承载关键词时才使用 H3
- 不允许从 H1 直接跳到 H3，也不允许用多个 H1 模拟章节标题

### 2.3 H 标签交付检查

交付前必须输出标题树并校验：

- H1 数量等于 1
- 同级 Methods 使用同级标题
- 标题层级连续
- 标题与正文主题一致
- H2/H3 自然覆盖长尾词和场景词，不堆砌关键词

## 3. 搜索意图与 Methods 选择

### 3.1 先理解用户为什么搜索

Methods 不能由模板数量决定，必须由搜索意图决定。先识别：

- 用户要完成的核心任务
- 用户可能拥有的设备、素材状态、预算和技术能力
- 用户是否在寻找免费、手动、在线、桌面或专业方案
- 用户关心的结果质量、速度、隐私、学习成本和可逆性
- PAA、搜索下拉词、论坛问题和 SERP 中出现的子需求

### 3.2 建立候选方案池

从以下来源寻找并去重可行方案：

- 官方或原生方法
- 免费或手动方法
- 系统自带或常见工具
- 在线方案
- 专业软件方案
- 论坛中被真实用户验证的特殊方法
- 自有产品方案

自有产品必须进入产品适配评估；适配当前内容对象和核心任务时，作为候选方案池中的一个正式 Method 参与评估。若不适配当前核心任务但具备相邻场景价值，不能进入正式 Methods 矩阵，应转入 Ultra-Tips 评估。

### 3.3 方法数量与保留条件

- Method 数量不设固定模板，也不能在调研前预先指定；必须先建立完整候选方案池，再根据可行性、场景差异和用户决策价值去重、合并和保留
- 通常保留 2 至 4 个能够覆盖不同用户场景的方法
- “2 至 4 个”是常见成稿范围，不是硬性下限、上限或生成目标；调研证明需要更多有效方案时可以超过 4 个，只有有限可行方案时也可以少于 2 个，但必须记录依据
- 每个 Method 必须解决一个明确场景，不能只是换一个工具重复同一做法
- 若只保留一个 Method，必须提供可核验依据，证明没有其他可行方案；否则大纲不得通过
- 正式产品方案计入 Methods 总数，并与其他方法接受同一套适用性和真实性评估
- Ultra-Tips 不计入 Methods 数量，不得用来制造“方法数量”或替代缺失的主方案
- 若存在权威官方方案，可先介绍官方方案；产品方案按综合价值安排顺序

### 3.4 方法排序

排序依据是用户决策价值，不预设任何 Method 的固定位置，也不是固定把产品放在第一位或第三位：

- 意图匹配度
- 成功概率和结果质量
- 操作难度
- 成本和时间
- 对素材或设备的风险
- 产品转化目标

自有产品必须进入产品适配评估；只有调研证明其能够直接有效解决当前问题时才进入最终 Methods。入选后与其他方案使用同一评估标准，并根据意图匹配度、成功概率、操作门槛、风险和内容叙事逻辑安排在最合适的位置。若不能直接解决当前问题但能提供相邻价值，则按 Ultra-Tips 规则处理。

当产品确实是综合最佳方案时，可将其标为 Best Overall、Best for [具体场景] 或 Most Reliable，并用后文证据支持。不能先写“best”，再补理由。

### 3.5 竞品内容分析前置要求

Methods 和文章结构不能只由模板生成。写 Brief 前必须完成竞品内容分析：

- 分析当前排名页面如何理解用户意图
- 提取并去重竞品覆盖的解决方案
- 比较竞品的 Quick Answer、Methods、步骤、场景分流、案例、FAQ 和 Verdict
- 分析竞品的关键词、长尾需求、PAA 和主题实体覆盖
- 判断排名页面在内容层面可能做对了什么
- 找出竞品共性、内容差距、错误和可超越机会
- 明确我们必须覆盖、必须写得更好、需要差异化和必须避免的内容

具体执行遵循《竞品内容分析标准 v1》。竞品分析没有形成内容机会矩阵时，不能进入 Content Brief。

## 4. 文章推荐结构

1. Title 与唯一 H1
2. Introduction：痛点、场景、解决承诺和阅读价值
3. Quick Answer：用 60 至 120 字给出方法总览和选择建议
4. Requirements：必要工具、备份、设备和素材准备
5. Methods Overview：方法、适用场景、成本、难度、效果和限制对比
6. Method 1 至 Method N：逐一完整展开
7. How to Choose：按 use case 帮用户选方法
8. Professional Case 或 Tested Example：支持产品方案的专业案例
9. Common Mistakes：常见错误和修正方式
10. FAQ：覆盖真实搜索问题
11. Verdict：按场景给出明确结论
12. CTA：在价值说明和步骤之后给出行动入口

结构可按主题调整，但 Quick Answer、多个 Methods、产品完整步骤、场景分流和 Verdict 不得无理由删除。

## 5. 所有 Method 的统一写作要求

每个 Method 都必须包含：

- 方法名称和一句话结论
- 最适合的具体场景和用户
- 能解决的问题与不能解决的问题
- 所需工具、成本、时间和前置条件
- 可执行步骤
- 预期结果
- 至少一个专业提示
- 优点、限制和风险

先告诉用户怎么做，再解释为什么有效，最后说明注意事项。

## 6. 产品 Method 的高转化写作要求

产品 Method 不是功能列表，必须是一段完整、独立、可执行、可验证的解决方案。

### 6.1 场景诊断

开头必须明确：

- 当前素材或用户场景
- 用户正在遇到的具体问题
- 普通方法为什么不足
- 产品适合解决其中哪一部分
- 使用后的合理结果预期

禁止使用“功能强大”“一键增强”“适合各种场景”等没有场景证据的通用表述。

### 6.2 功能与场景映射

只能引用产品知识库中已确认的功能，并写清：

`场景问题 -> 对应功能/模型 -> 设置或操作 -> 预期改善 -> 边界`

不能先罗列功能，再让用户自己推断该用哪个功能。

### 6.3 详细步骤

产品 Method 至少包含以下操作链路，具体名称以当前产品版本为准：

1. 准备并备份原始素材
2. 导入文件
3. 根据当前场景选择功能或模型
4. 设置与场景相关的参数
5. 预览并比较结果
6. 调整设置或处理异常
7. 导出并保存适合后续使用的版本

每一步必须包含“做什么 + 为什么 + 当前场景的设置建议”。不能只写 Download、Upload、Enhance、Export 四个空泛动作。

### 6.4 专业案例

当产品被定位为最佳方案时，至少提供一个专业案例或可验证的测试示例：

- 输入素材：来源、年代、分辨率、损坏或质量问题
- 目标：用户希望恢复到什么用途
- 操作：使用的功能、模型和关键设置
- 结果：改善了什么，仍保留什么限制
- 专业判断：为什么选择该方案，而不是其他 Method

没有真实数据时，必须标记为“建议测试方案”或“示例工作流”，不得虚构测试结果、用户评价或数值。

### 6.5 说服顺序

产品 Method 按以下顺序组织：

`场景共鸣 -> 方案判断 -> 功能匹配 -> 详细步骤 -> 结果证据/案例 -> 限制 -> CTA`

CTA 必须出现在用户已经理解产品为什么适合、如何使用和能得到什么结果之后。

## 6.6 跨内容对象产品的 Ultra-Tips 推荐规则

Ultra-Tips 用于推广一个不能直接解决文章主任务、但能解决相邻问题的产品。例如：文章主任务是移除视频水印，而产品只支持图片水印处理时，产品不能成为视频 Method，但可以在文章后半段推荐其图片水印清理能力。

### 6.6.1 进入条件

只有同时满足以下条件，产品才能进入 Ultra-Tips：

- 产品事实已经由知识库和官网资料确认
- 产品确实能解决一个与当前主题相关的相邻需求
- 相邻需求在用户场景中真实存在，而不是为了植入产品临时制造
- 文章已经完整提供当前主任务的正常解决方案
- Ultra-Tips 不会让用户误以为产品可以解决当前主任务
- 产品推荐的位置、标题和措辞均明确标注其补充性质

### 6.6.2 推荐位置

Ultra-Tips 不得出现在 Quick Answer、主方法总览或正式 Methods 之间。推荐位置优先为：

- 主要 Methods 完成之后、How to Choose 之前或之后的补充模块
- 与相邻图片、素材或后续工作流直接相关的 use case 之后
- Verdict 之前的“Related Cleanup Tip”或“Ultra-Tip”模块

具体位置由用户路径决定，但必须先解决主问题，再介绍补充能力。

### 6.6.3 固定内容结构

Ultra-Tips 必须包含：

1. 明确标签：`Ultra-Tip`、`For the image version` 或等价表达
2. 适用的相邻场景
3. 明确说明不适用于当前主任务的部分
4. 产品能解决的具体补充问题
5. 结合该场景的操作步骤
6. 格式、大小、登录、隐私和结果限制
7. 版权与授权提醒
8. 适合继续了解或尝试的 CTA

### 6.6.4 禁止写法

- 把图片工具写成视频去水印工具
- 用“同样可以处理”“也能解决这个问题”等模糊连接掩盖能力边界
- 把 Ultra-Tips 计入正式 Methods 数量
- 在文章开头或 Quick Answer 中优先推荐不兼容产品
- 在没有主任务解决方案的情况下，用 Ultra-Tips 代替正常方案
- 使用“一键、完美、支持所有格式”等未经证实的承诺

### 6.6.5 Ultra-Tips 价值标准

Ultra-Tips 不是单纯广告位，必须回答：

- 用户在完成主任务后还可能遇到什么相邻问题
- 为什么这个产品适合补充处理该问题
- 用户具体应该怎么操作
- 产品当前不能做什么

推荐结构：

`主任务已解决 -> 相邻问题出现 -> Ultra-Tip 适用边界 -> 场景步骤 -> 限制 -> CTA`

## 7. 方法比较与 Verdict

比较表至少包含：

- 最适合的场景
- 成本
- 难度
- 时间
- 结果质量
- 可控性
- 主要限制

Verdict 必须按 use case 做选择：

- 想快速、低成本完成基础处理时选什么
- 想保留原始素材或手动控制时选什么
- 想获得更稳定、更专业结果时为什么选产品

结论必须由前文步骤、比较和案例支持，不能突然把产品宣布为最佳方案。

## 8. 交付验收门槛

出现以下任一情况，文章不得交付：

- H1 不唯一，或普通模块被误设为 H1
- 搜索意图没有转化为 Methods 选择依据
- 存在多个可行方案却只写一个
- 产品没有作为正式 Method 进入方案矩阵
- 产品被放在 Methods 之外单独硬插
- 产品与当前内容对象不兼容，却被写成正式 Method
- Ultra-Tips 出现在主方法之前、Quick Answer 或主方法总览中
- Ultra-Tips 没有明确说明其只解决相邻问题
- Ultra-Tips 被计入 Methods 数量或替代主任务解决方案
- Ultra-Tips 只有产品卖点，没有当前场景、步骤和限制
- 产品段落只有通用功能，没有场景诊断和功能映射
- 产品步骤不完整或无法照着执行
- 产品被称为最佳方案，却没有比较依据或专业案例
- 产品事实未经知识库校验
- Quick Answer、use case、有效步骤或 FAQ 在优化时被无理由删除
- 未经过竞品内容分析就直接确定 Methods 和大纲
- 文章只复刻竞品共性，没有明确的差异化价值

## 9. 增量优化原则

优化已有文章时，先锁定必须保留的高价值模块，再修补弱项：

- 默认保留 Quick Answer、有效 use case、正确的产品步骤、专业案例、稳定 FAQ 和有效结论
- 优先修补 Methods 覆盖、H 标签层级、关键词布局、产品场景贴合度和事实精度
- 只有主题偏离、事实严重错误或章节逻辑无法局部修复时，才允许整体重构
- 新增 Method 时，应插入方案总览、正文、比较表和 Verdict 的对应位置，不能破坏原有有效模块
